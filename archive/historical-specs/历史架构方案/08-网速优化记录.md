---

## 1. 一句话

> **慢的原因不是服务器带宽，是家宽到国外的国际段在丢包。**
> 所以换协议（TCP → QUIC）有效，升配置/换套餐无效。

---

## 2. 诊断：先证明瓶颈在哪

优化前必须先排除「服务器不行」。在服务器本机测（不受家宽限制）：

| 机器 | 服务器自身下载 | 从家里经该节点 | 差多少 |
|---|---|---|---|
| 硅谷 43.153.56.137 | **121 Mbps** | 12 Mbps | **10 倍** |
| 新加坡 43.163.4.104 | **125 Mbps** | 3MB 都下不完 | — |

**两台服务器都有 100 Mbps 以上的能力，家里只拿到十几 Mbps。**
→ 瓶颈在 **家宽（黑龙江移动）到国外的国际段**，不在机器、不在套餐、不在 CPU。

### 2.1 排除掉的三条

| 假设 | 证据 | 结论 |
|---|---|---|
| 套餐带宽小（5Mbps） | 服务器实测 121 Mbps | ❌ 排除 |
| 服务器性能不足 | 4 台均为轻量，实测出口百兆 | ❌ 排除 |
| mux 拖慢 | `config.json` 里无 mux 字段 | ❌ 排除 |

### 2.2 为什么换成 QUIC 有效

VLESS + Reality 跑在 **TCP** 上。TCP 一遇丢包就把拥塞窗口砍半，在国际长肥管道（RTT 220ms）上恢复极慢——表现就是「1MB 还行、3MB 卡死」。

Hysteria2 基于 **QUIC**，自带类 BBR 的拥塞控制，对丢包不敏感。这是换协议能提速 46% 的原因。

---

## 3. 改了什么

### 3.1 服务器（硅谷 43.153.56.137）

| # | 改动 | 位置 |
|---|---|---|
| 1 | 拥塞控制 `cubic → bbr`，队列 `fq_codel → fq` | `/etc/sysctl.d/99-bbr.conf`（持久化） |
| 2 | 加载 `tcp_bbr` 模块 | `/etc/modules-load.d/bbr.conf` |
| 3 | 新增 **Hysteria2 入站**：`443/udp`，ALPN h3，obfs=salamander | `/opt/sing-box/config.json` |
| 4 | 生成自签证书（10 年，CN=www.bing.com） | `/opt/sing-box/hy2.crt` / `hy2.key`（key 权限 600） |
| 5 | 腾讯云防火墙放行 **UDP 443** | 轻量防火墙规则，备注 `hysteria2` |

**原有 Reality（443/tcp，VLESS+Vision）保持不动**，两条并存：同一台机器、同一个 IP，TCP 和 UDP 各走一条。

### 3.2 云防火墙

| 协议 | 端口 | 说明 |
|---|---|---|
| TCP | 443 | Reality（原有） |
| UDP | 443 | Hysteria2（新增） |
| TCP | 8443 / 80 / 22 / 8888 | 原有 |

放行动作是通过项目自带的 `server/providers/tencent.py` 调腾讯云 API 完成的（`CreateFirewallRules`），没有手工点控制台。

> 注意：原 `open_port()` **只支持 TCP**（硬编码 `"Protocol": "TCP"`）。这次是靠临时脚本直接调 `_call()` 加 UDP 规则的。**这是 provider 层的一个已知缺口**，见第 7 节。

### 3.3 面板代码（/opt/web）

| 文件 | 改动 | 为什么 |
|---|---|---|
| `admin.py` | 新增 `hy2(n)` 生成分享链接；新增 `link(n)` 按 `type` 分发；`render()` 里 `vless(n)` → `link(n)` | 否则每次节点变动重新渲染，HY2 会被**静默丢掉** |
| `probe.py` | 遇到 `type=hysteria2` 直接 `continue` | 443 端口同时跑 Reality，TCP+TLS 探活会给出**假绿灯**（本项目历史上最贵的 bug 类型） |
| `nodes.json` | 新增一条 `硅谷-HY2`：`type=hysteria2`、`password`、`obfs_password`、`sni=www.bing.com`、`health=ok` | 进订阅、进面板 |

### 3.4 数据模型变更（新增字段）

```json
{
  "name": "硅谷-HY2",
  "type": "hysteria2",          // 新增：缺省视为 vless，老数据不用迁移
  "host": "43.153.56.137",
  "port": 443,
  "password": "...",             // 仅 hysteria2
  "obfs_password": "...",        // 仅 hysteria2
  "sni": "www.bing.com",
  "source": "builtin",
  "health": "ok",
  "exit_ip": "43.153.56.137",
  "exit_country": "US"
}
```

> **向后兼容**：旧节点没有 `type` 字段，`link()` 默认按 vless 处理，不需要迁移。

## 5. 北京中转：结论被推翻（2026-10-27 更正）

原本这里写的是「北京中转不推荐」，依据是：

    硅谷 → 北京 RTT 153.9ms，5 个包丢 1 个（20%）

**这个依据是错的。** 2026-10-27 拿到北京的 root 权限后实测：

    ping 43.153.56.137（北京 → 硅谷）
    5 packets transmitted, 5 received, 0% packet loss
    rtt avg = 151.9ms  (mdev 0.015ms)

    北京 → Cloudflare 下载 10MB
    速度 3.59 MB/s = 28.7 Mbps

**0% 丢包，28.7 Mbps。**

之前的 20% 是从硅谷那一侧 ping 北京测出来的——那是**北京对 ICMP 的限速**，不是真实丢包。我用一个被限速的指标，否定了一个可能有效的方案。

### 重新算一遍账

| 路径 | RTT | 可用带宽 |
|---|---|---|
| 家宽 → 硅谷（直连） | 220 ms | 17.6 Mbps |
| 家宽 → 北京 → 硅谷 | 约 35 + 152 = **187 ms** | 上限 **28.7 Mbps**（北京出口）|

**中转可能比直连更快**，和原来的结论相反。

### 实测结论（2026-10-27 09:58 · 客户端切到北京节点）

| 大小 | 直连硅谷（HY2） | **经北京中转** | 结果 |
|---|---|---|---|
| 1MB | 4.80 Mbps / 首字 0.52s | 2.25 Mbps / **首字 2.02s** | ❌ 差 2 倍 |
| 2MB | 14.47 Mbps | 2.90 Mbps | ❌ 差 5 倍 |
| 5MB | 15.61 Mbps | 4.07 Mbps | ❌ 差 4 倍 |
| 10MB | 17.58 Mbps | **18 秒没下完** | ❌ 失败 |

**中转实测是直连的 1/4，首字延迟 4 倍。** 链路核实过是真的走了北京（北京 24 条 :443、硅谷有 17 条来自北京的连接）。

**为什么「北京自己跑 28.7 Mbps」但中转只有 4 Mbps**：北京本机 curl 是一条 TCP；中转要维护「客户端→北京」和「北京→硅谷」两段 TCP，两段各自拥塞控制，152ms 的长肥管道上叠加后直接塌。**单机测速不能代表中转能力。**

**结论：北京中转否决，保留为备用，日常用硅谷-HY2。**

### 再更正一次（2026-10-27 12:20）：把出站也换成 HY2，结果指向别处

试过把北京的 outbound 从 Reality(TCP) 换成 Hysteria2(QUIC)，想让中转两段都抗丢包。结果：

| 路径 | 结果 |
|---|---|
| 北京 → 硅谷 ping | **10 个包丢 4 个（40%）**，RTT 153ms |
| 北京 → 硅谷 经 Reality(TCP) 1MB | 13.5 KB/s |
| 北京 → 硅谷 经 Hysteria2(QUIC) 1MB | 14.3 KB/s |
| 北京 → Cloudflare **直连** 1MB | **317 KB/s** |

**两种协议表现一样烂。** 而同一时刻北京直连 CF 是正常的。

这说明：**瓶颈不是"两段 TCP 叠加"，是北京↔硅谷这条国际链路的丢包。**
10:30 量的时候是 0% 丢包，12:20 量变成 40%——**这条链路是时变的**。

**我上一版把 4 Mbps 归因于"TCP 串 TCP"，这个解释是错的。**
QUIC 在 40% 丢包下也救不回来，说明问题在链路质量本身，不在协议选择。

**已回滚**：北京 outbound 恢复为 Reality，配置来自 `config.json.bak-before-hy2out-<时间戳>`。
