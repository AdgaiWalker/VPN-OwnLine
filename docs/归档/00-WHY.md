# 决策记录（ADR）

每个决定都写了**代价**。没有免费的架构。

---

## ADR-001 用 VLESS + Reality，不用 vmess/ws/tls

**背景**：2020 年后，带证书的 TLS 代理（vmess+ws+tls、trojan）在主动探测下容易暴露——服务器有证书、有域名、有固定指纹。

**选项**：
| 方案 | 优点 | 致命缺点 |
|---|---|---|
| Shadowsocks | 简单 | 流量特征明显，已被大规模识别 |
| vmess + ws + tls | 兼容性好 | 需要域名和证书；TLS 指纹是服务器自己的 |
| trojan | 伪装成 HTTPS | 同上，且证书必须真实有效 |
| **VLESS + Reality** | 不需要域名/证书；握手借真实网站；无自签证书特征 | 配置参数多（公钥/短ID/SNI 必须完全一致） |

**决定**：Reality。节点机器不需要域名，443 端口对外就是一个正常的 TLS 站点。

**代价**：
- 参数多，错一个字符就连不上（客户端表现是"握手失败"，没有任何提示）
- 服务端会往日志里写 `REALITY: processed invalid connection`——这是**正常现象**（探活或扫描器触发的回落），不是故障
- 部分老旧客户端不支持

**何时该推翻**：如果你的网络环境对 Reality 有针对性封锁，换 Hysteria2（UDP，抗丢包强，但部分网络封 UDP）。

## ADR-002 套 Cloudflare，并把面板放 8443

**问题**：一台机器既要做面板（HTTPS 网站），又要做节点（443）。同一个 443 不能两用。

**选项**：
1. 面板用域名 + 节点用别的端口 → 节点端口非标，容易被识别
2. 面板放 8443，Cloudflare 回源改写 → 节点独占 443

**决定**：方案 2。Cloudflare 免费套餐只代理 80/443，回源端口用 **Origin Rule** 改成 8443。

**代价**：链路变成四个环节，**任一环节错都会挂**，且错误现象互相掩盖：

```
DNS(橙色云) → SSL模式(Full) → Origin Rule(8443) → 云防火墙(放行8443)
```

见 [03-FAILURE-MODES.md](03-FAILURE-MODES.md) 的排查表。

**收益**：源站 IP 不进 DNS；被墙时只改一条 A 记录，节点参数全部不变。

## ADR-003 面板是单页 HTML，不用框架

**背景**：使用者不是工程师，面板要能在任何设备上打开、加载快、不需要构建。

**决定**：一个 `index.html`，内联 CSS/JS，无 npm、无打包、无 CDN 依赖。

**代价**：
- 4 万字符的单文件，改起来要靠 grep 定位
- 没有组件化，重复样式只能靠 CSS 变量和 class 约定

**收益**：改一行就能上线，不需要 `npm run build`；断网也能打开（无外部资源）。

## ADR-004 流量数据以 IP 为键，不用节点名

**背景**：节点可以改名（"Ubuntu-TfPo" → "北京"）。

**决定**：`usage.json` 用 `{ "198.51.100.14": {...} }`，前端按 `node.host` 查。

**代价**：同一 IP 上跑两个节点会串数据（现实中不会发生）。

**收益**：改名不会导致流量数字错位——这个 bug 我们真踩过。

## ADR-005 安装用"后台任务 + 轮询"，不用长连接

**背景**：装一台机器要 30 秒~10 分钟（取决于下载速度）。HTTP 长连接会被 Cloudflare 100 秒超时切断。

**决定**：
```
POST /api/addnode → 立刻返回 job id
GET  /api/job?id=  → 每 800ms 拉一次 {state, step, log}
```

**代价**：任务状态在内存里，**重启 admin 服务会丢任务**（前端要能处理"任务不存在"）。

**收益**：进度条能实时走，不会因为网络抖动中断。

## ADR-006 探活用 TCP + TLS 握手，不用真客户端

**背景**：判断"节点是否可用"最准的方法是跑一个真客户端连上去。但那要维护 4 份配置、消耗 CPU。

**决定**：先 TCP 连端口，再 openssl 握手看证书。两者都通就算在线。

**代价**：**会误报**——端口通、TLS 通，但 Reality 参数错了，探活依然显示绿色。真实链路的验证只能靠用户。

**收益**：一次探活 1 秒内完成，4 个节点 60 秒一轮毫无压力。

## ADR-007 不装第三方面板（3x-ui 教训）

**当时**：为了"少写代码"，先装了 3x-ui，想复用它的节点管理。

**结果**：安装脚本 `/tmp/3x.sh` 被腾讯云主机安全判定为**恶意文件**，触发短信告警，用户要求立即删除。整轮卸载、清防火墙、删 fail2ban。

**结论**：云厂商的安全产品会对"面板类软件"高度敏感。**自建面板 = 只跑自己的代码**，反而更安全、更可控。

## ADR-008 云厂商必须抽象成 provider

**背景**：最初腾讯云的 API 调用散落在 `admin.py`、`usage_refresh.py`、`usage.py` 三处，共 19 行。

**问题**：换一家云，三条自动化（开防火墙、重置密码、看流量）全部消失，只剩"手动输密码"。

**决定**：

```
providers/base.py       接口
providers/generic.py    通用兜底（只给手动指引）
providers/tencent.py    腾讯云实现
providers/__init__.py   注册表 + 逐个尝试
```

核心代码只调 `providers.open_port()` / `providers.reset_password()`，不认识任何一家云。

**代价**：多一层间接，调试时要多看一个文件。

**收益**：接阿里云 = 加一个文件 + 注册一行，**不改任何核心逻辑**。见 [02-PROVIDERS.md](02-PROVIDERS.md)。
