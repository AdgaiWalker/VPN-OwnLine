# 七个最贵的 Bug

这个仓库有 14 个故障记录、8 条决策。但如果只读一页，读这页。

七个 bug 都不是技术难题。它们的共同点是：**以为自己想清楚了，但没有让系统强制住。**

前三个是搭建期踩的。后四个是 2026-10-27 做「陌生人演练」时踩的——
那天把代码交给一台干净的机器，只照文档走，不许用文档以外的知识。

---

## 一、把「我知道原因」当成「用户也知道」

### 现象

用户在页面上加节点，看到：

```
STEP 1 正在连接服务器
（然后什么都没有了）
```

不知道是密码错、网络断、还是程序崩了。只能截图来问。

### 代码长这样

```bash
sshpass -p "$PASS" ssh ... "uname -m" 2>/dev/null   # 错误信息扔进垃圾桶
set -e                                              # 一出错静默退出
```

写这两行的时候，我的想法是"这条命令的报错太吵了，屏蔽掉"。**但用户看到的不是"安静"，是"死掉"。**

### 代价

一来一回 40 分钟，而且我一开始还判断错了方向（以为是 22 端口不通，实际是 GitHub 下不动）。

### 本质

报错信息在代码里被"优化"掉了，因为**写代码的人不需要它，读报错的人需要它**。这两种人不是同一个。

### 怎么防

**失败路径必须有输出，且输出必须回答「下一步做什么」。**

```bash
if ! OUT=$(sshpass ... 2>&1); then
  echo "连接失败：$OUT"        # 先说事实
  exit 1
fi
```

然后在展示层把它翻译成人话：

| 日志里的信号 | 页面显示 |
|---|---|
| `Permission denied` | 密码不对 → 去控制台重置密码 |
| `curl: (56)` | 服务器下载失败 → 这台连不上 GitHub |
| `timed out` + `ssh: connect` | 连不上 22 端口 → 查防火墙 |

### 检验方法

**随便断掉一个环节**（改错密码、关掉端口、停掉服务），看页面说什么。
如果它说的是"失败了"，那就是没做完。

## 二、默认值是设计决策，不是小事

### 现象

"添加节点"的列表里，默认选中了第一项——而第一项是**正在用的节点**。
用户一路点"下一步"，把自己的生产节点重装了。

### 代码长这样

```js
rows[0].click()          // 打开就选中第一个
nextBtn.disabled = false // 下一步永远可点
```

### 代价

真的断线过。而且用户不知道自己做了什么。

### 本质

**默认值是"用户不做选择时的选择"**，它比显式选项更重要——因为大多数人不会去改它。

一个危险操作，如果默认值是安全的，用户要主动犯错才会出事；
如果默认值是危险的，用户要主动小心才不出事。**后者注定会出事。**

### 怎么防

```
□ 不预选任何一项（下一步按钮初始禁用）
□ 选中"已经在用"的机器 → 标红 + 二次确认
□ 删除类操作 → 弹层确认，不用浏览器原生 confirm（原生的样式丑，用户会条件反射点确定）
```

### 检验方法

**打开页面，什么都不点，看会发生什么。**
如果一个危险操作在"什么都不做"的情况下会发生，那就是设计错误。

## 三、把「我不打算」当成保险

### 现象

为了验证 provider 路由，我写了一段测试：

```python
# 只查权限，不真重置   ← 注释是这么写的
st, msg, extra, who = providers.reset_password('198.51.100.14')
```

结果**真的执行了**：那台机器 root 密码被改成随机串（没打印出来，等于丢了），机器重启。

### 代价

密码丢失、服务中断 1 分钟。幸运的是 SSH 密钥还在，节点没死。

### 本质

**注释不能约束代码，只有分支能。**

"我不打算真的执行"是一个人的意图，不是一个程序的状态。程序只看代码怎么走，不看注释怎么写。

### 怎么防

```python
def reset_password(self, ip, dry_run=False):
    if dry_run:
        return ("dry", "会把 xxx 的密码重置并重启（未执行）", {})
    # 真正的副作用在这里
```

再加两条：

1. **查权限用只读接口**（`DescribeFirewallRules`、`DescribeInstances`），
   不要用写接口去"探一下有没有权限"
2. **任何会改变外部状态的函数，在写下的那一刻就要有干跑模式**——
   不是"小心一点"，是"让它不可能误执行"

### 检验方法

**把最危险的函数单独拿出来调用一次**，看它有没有一条"什么都不做"的路。
没有的话，它迟早会被误调用。

## 四、把「命令没报错」当成「事情做成了」

### 现象

安装脚本跑完，全程绿色对勾。打开浏览器，面板打不开。

### 代码长这样

```bash
apt install -y caddy          # 装完 systemd 自动把它拉起来了
cat > /etc/caddy/Caddyfile …  # 写新配置
systemctl enable --now caddy  # ← 对已经在跑的进程，这是空操作
```

结果：Caddy 从头到尾跑的是**旧的默认欢迎页配置**，我们写的 8443 站点根本没加载。

### 代价

装完等于没装。而且脚本第 7 步还会「自检通过」——因为它检查的是进程在不在，不是配置生不生效。

### 本质

**`enable --now` 的语义是「确保它是启用的、并且是跑着的」，不是「让它重新读一遍配置」。**

这件事在同一个项目里发生过两次：第一次是 2026-10-26 的 code review，第二次是今天的安装脚本。**同一个坑踩两次，说明第一次只改了代码，没改习惯。**

### 怎么防

改完配置，一律 `restart`，不用 `reload` 除非确认支持热加载；`enable --now` 只用来做「第一次拉起」。

### 检验方法

装完之后，**不要看进程状态，看端口**：

```bash
ss -lntp | grep 8443   # 空的就说明配置没生效
```

## 五、重跑一次安装，把上一次的成果毁掉

### 现象

第一次装好，手机导入订阅，一切正常。第二次跑同一个安装脚本（想改个域名），输出里 token 变了：

```
订阅地址 https://xxx/s/febf3ccbbc0c   ← 第一次
订阅地址 https://xxx/s/709655c0eb7a   ← 第二次
```

### 代价

所有已导入的设备同时失效。面板密码也一起被换了。用户不会收到任何提示。

### 本质

脚本每次执行都**重新生成**凭据，而不是**只在缺失时生成**。

这是「幂等」的反面：**一个应该可以安全重跑的操作，第二次跑就破坏了系统状态。**

### 怎么防

凡是生成凭据的地方，先问一句：**已经存在吗？存在就保留。** 覆盖已有配置之前，必须显式告诉用户会发生什么。

### 检验方法

**连跑两次，看第二次的输出有没有变化。** 变了就说明不幂等。

## 六、用一个被污染的指标，否掉一个正确的方案

### 现象

想验证「国内机器做中转会不会更快」。从海外机器 ping 国内机器：

```
5 packets transmitted, 4 received, 20% packet loss
```

结论：中转丢包 20%，方案否决。

### 代价

方案被否了两个月。后来拿到国内机器的权限，在它自己身上测：

```
5 packets transmitted, 5 received, 0% packet loss
```

**假的。** 那 20% 是**对方对 ICMP 限速**，不是真实丢包。

### 本质

**测量工具本身会引入偏差，而偏差往往方向一致、看起来很像真数据。** 在那个位置，ping 是最容易拿到的指标，也是最能骗人的指标。

### 怎么防

同一个结论，至少用两种不同机制去验证：ICMP 之外用 TCP 握手，本机之外用第三方节点。**指标冲突时，先怀疑工具，再怀疑结论。**

### 检验方法

问自己一句：**这个数字，有没有可能是被限速 / 被缓存 / 被重写出来的？**

## 七、把「我数到的」当成「事实的全部」

### 现象

交付前检查仓库，发现 38 个 `.pyc` 文件，判定「编译产物被提交进仓库了」，写进了发布阻塞清单。

### 代价

准备花时间做 `git rm --cached`。实际上：

```bash
git ls-files "*.pyc"   # 0
git ls-files | wc -l   # 54
```

**一个都没被跟踪。** 那 38 个是我自己跑测试时在磁盘上生成的，`.gitignore` 早就挡住了。

### 本质

**我数的是「文件系统」，我以为我数的是「仓库」。**

同一天还犯过一次同类：看到新加坡的 sing-box 不是 Windows 服务，就断言「没有托管、重启就没了」——实际它是**计划任务**，开机自启、失败重启 999 次。

### 怎么防

下判断之前，先确认**你量的那个东西，和你要判断的那个东西，是不是同一个东西**。差一个 git、差一个服务管理器，结论就完全相反。

### 检验方法

每个否定性结论后面跟一条**可复现的命令**。写不出命令的判断，先别写进文档。

## 七条的共同点

| # | 我以为 | 实际 |
|---|---|---|
| 1 | 用户能猜到原因 | 用户只能看到"失败了" |
| 2 | 用户会看清楚选项 | 用户会一路点下一步 |
| 3 | 代码会听注释的话 | 代码只执行分支 |
| 4 | 命令没报错就是成了 | 进程跑着 ≠ 配置生效 |
| 5 | 脚本能重跑 | 重跑会换掉凭据 |
| 6 | ping 出来的就是真相 | 那可能是对方的限速 |
| 7 | 我数到的就是仓库里的 | 我数的是磁盘 |

**都是把"我的意图"当成了"系统的行为"。**

---

## 怎么用这七条审别人的代码

四个问题，几分钟能问出来：

1. **"把网络断掉，它说什么？"** → 检验失败路径
2. **"什么都不操作，默认会发生什么？"** → 检验默认值
3. **"把最危险的那个函数单独调用，会发生什么？"** → 检验副作用
4. **"连跑两次，第二次的结果和第一次一样吗？"** → 检验幂等

四个都答得清楚的，基本可以放心用。
答不上来的，说明它只是能跑，还不能给人用。

## 一条给自己的话

写代码时最容易省掉的四件事：

```
失败的输出
默认值的选择
副作用的开关
重跑一次会怎样
```

省掉的每一件，最后都会以"用户来问你"的形式回来——
而那时候的成本，是写它时的十倍。
